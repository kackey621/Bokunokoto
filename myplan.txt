ステップバイステップで、自己開示するWebページを作りたいと思っています。Webページには特殊なマスキングにて、スクリーンショットではブラックアウトして内容が見えず、印刷や共有も、テキストコピーもできないようにしたいです。また、アクセスできる人も段階によって変更できるようにしたいと思っています。そのために、ユーザー登録をFirebase Authを利用して実現したいと思います。

まず、そのためにAntigravityで作るために必要な設計書を考えたいです。協力をしてください。
自己開示を段階的に進めるWebページの設計、非常に興味深いプロジェクトですね。特に「スクリーンショットでのブラックアウト」や「コピー禁止」といった機密性の高い要件は、Web技術の限界に挑む部分もあり、工夫のしがいがあります。

2. セキュリティ機能設計（マスキング・持ち出し防止）
ブラウザの標準機能だけで完全なスクリーンショット防止は困難ですが、以下の多層防御により、一般的なユーザーによる複製を極めて困難にします。

A. スクリーンショット/録画対策 (Blackout)

CSS Overlay: コンテンツの上に、マウスホバーやフォーカス時以外は不透明度を調整するレイヤーを配置します。

動画再生APIの応用: ブラウザによっては、<video>タグで保護されたコンテンツがスクリーンショットで黒塗りになる特性があります。テキストをSVGやCanvas化し、それを動画ストリームとして流すことで、OSレベルのキャプチャをブラックアウトさせる手法を検討します。

B. テキストコピー・印刷の禁止

CSS制御:

CSS
body {
  user-select: none; /* テキスト選択禁止 */
  -webkit-touch-callout: none;
}
@media print {
  body { display: none; } /* 印刷時は内容を非表示 */
}
JavaScript制御: contextmenu（右クリック）、copy、keydown（Ctrl+C / Cmd+C / PrintScreen）のイベントをインターセプトし、動作を無効化します。

C. 特殊なマスキング（動的難読化）

Canvasレンダリング: テキストをDOMとして配置せず、HTML5 Canvas上に描画します。これにより、開発者ツールからのテキスト抽出を防止します。

フォント難読化: 特定のグリフがランダムに入れ替わるカスタムフォントを使用し、コピーしても意味をなさないようにします。

2. DRM的ブラックアウトの実装 (Screen Capture Prevention)
Web標準でOSレベルのスクリーンショットを完全に「黒塗り」にするのは難易度が高いですが、以下のEME (Encrypted Media Extensions) 的なアプローチを組み合わせて防御を固めます。

A. Video Stream への変換 (高強度)

静的なテキストや画像をそのまま表示せず、Canvasで描画した内容を captureStream() で動画化し、<video> タグで再生します。

多くのブラウザやOSのキャプチャ機能は、動画コンテンツ（特にDRM保護フラグが立っているもの）をキャプチャする際に、著作権保護のため自動的にブラックアウトさせる特性があります。

B. display-capture 権限の検知

ブラウザが画面共有や録画を開始しようとした際、navigator.mediaDevices.getDisplayMedia のイベントを監視し、検知した瞬間にコンテンツを display: none またはブラックアウト画像に差し替えます。

C. 開発者ツールの徹底ブロック

debugger ステートメントのループによるスクリプト停止。

F12 や Ctrl+Shift+I のキーイベント無効化。

統合設計：Antigravity セキュリティ・シールド
単体では突破されやすい各機能を、一つのエコシステムとして機能させます。

1. レンダリング・パイプライン（Aの強化）

テキスト情報をそのままDOM（HTML）に書き出さず、以下の経路で表示します。

データ取得: Firebaseから暗号化されたデータを取得。

メモリ内展開: JavaScriptのメモリ上でのみ復号（DOMには出さない）。

Canvas描画: 非表示の canvas 要素にテキストを描画。

ビデオ変換: canvas.captureStream(fps) を実行し、そのストリームを <video> タグに流し込む。

DRM的保護: video タグに対して disablePictureInPicture や controlslist="nodownload" を付与。OSによっては、このビデオストリームがキャプチャソフトに検知された瞬間に黒塗り（Blackout）になります。

2. 適応型ウォッチドッグ（Bの監視）

ブラウザの状態を常に監視し、異常を検知した瞬間に「セルフデストラクト（画面消去）」を実行します。

キャプチャ・共有検知: navigator.mediaDevices.getDisplayMedia の呼び出し試行や、外部ディスプレイ接続の変更を監視。

フォーカス監視: visibilitychange や blur イベントをトリガーに、ユーザーがブラウザから離れたり、スクリーンショットのショートカットキー（OSレベル）を叩こうとした瞬間に画面を真っ黒にします。

3. 環境ロック（Cの隠蔽）

ソースコードやメモリからの情報抽出を徹底的に困難にします。

Anti-Debugger: 無限ループする debugger ステートメントをバックグラウンドで走らせ、デベロッパーツールを開いた瞬間にブラウザのタブをフリーズさせます。

コード難読化: 変数名やロジックを解読不能な状態にビルド。

右クリック・ショートカット無効化: contextmenu や F12、Ctrl+U、PrintScreen などのキー入力を完全にインターセプトします。

A. 技術的課題と解決策

Canvas/Videoストリームでマスキングを行うと、ブラウザの標準機能である「テキスト選択してCtrl+C（右クリックコピー）」が物理的に不可能になります。
これを解決するために、「セキュア・クリップボードAPIパターン」を採用します。

視覚情報の保護： 口座番号などの情報は、これまで通りCanvas経由でVideoタグにレンダリングし、画面キャプチャをブラックアウトさせます。

コピーの実現： Videoタグの横に専用の「コピーする」ボタンを配置します。

Clipboard API： ボタンがクリックされた時のみ、JavaScriptのメモリ上に保持している口座番号の文字列を navigator.clipboard.writeText() を使って直接OSのクリップボードに流し込みます。

B. UI/UXフロー（一つだけ選んで表示）

「ユーザーが一つだけ口座を選んで見る」という要件に対するフローです。

選択画面： 銀行名（例：A銀行、B銀行）のラジオボタンまたはドロップダウンを表示。この時点では口座番号は伏せ字（***-****）。

3. セキュリティルールの実装 (Firebase Security Rules)
ここが「Antigravity」の核心部分です。サーバーサイドで物理的にアクセスを遮断します。

JavaScript
service cloud.firestore {
  match /databases/{database}/documents {
    match /qa_contents/{qaId} {
      
      allow read: if request.auth != null && (
        // 1. 全員公開
        resource.data.visibility == "global" ||
        
        // 2. 段階的公開 (ユーザーのレベルを取得して比較)
        (resource.data.visibility == "tiered" && 
         get(/databases/$(database)/documents/users/$(request.auth.uid)).data.level >= resource.data.requiredLevel) ||
        
        // 3. 単なる返信 (本人のみ)
        (resource.data.visibility == "direct" && resource.data.askerUid == request.auth.uid)
      );
      
      // 質問の投稿はログインユーザーなら誰でも可能
      allow create: if request.auth != null;
    }
  }
}

1. 10段階のアクセス権限マップ（Level 0 〜 9）
各レベルにおける閲覧対象と、適用されるセキュリティ強度の定義です。

レベル	呼称	対象（イメージ）	セキュリティ強度	主なコンテンツ
L0	Public	未ログインの全ユーザー	なし	概要、公開プロフィール
L1	Guest	ログイン済みの一般ユーザー	低（コピー禁止のみ）	基本的な活動履歴
L2	Verified	メール認証済みのユーザー	低	質問箱への投稿権限
L3	Social	SNS等で繋がりのある人	中（ウォーターマーク）	Q&A（一般）
L4	Business	面識のあるビジネス関係者	中	Q&A（仕事関連）、口座番号
L5	Trusted	NDA（秘密保持）締結相当	高（ABCシールド）	進行中のプロジェクト詳細
L6	Partner	共同創設者・主要取引先	高	収益モデル、契約書類案
L7	Exclusive	個別交渉中の重要人物	最高（+ 画面非活性化）	一回限り表示の機密情報
L8	Inner	家族・親友・最側近	最高	核心的な自己開示
L9	Master	自分（管理者）のみ	-	全データ、管理パネル
2. 拡張された権限判定ロジック
「10段階の階層（Level）」に「個別指名（Whitelist）」を組み合わせた判定式です。

判定アルゴリズム (Logical OR)

以下のいずれかが true であれば閲覧を許可します。

content.visibility == 'global'

user.level >= content.requiredLevel

content.permittedUsers.includes(user.uid) （個別指名）

content.askerUid == user.uid （本人返信）

3. 技術的実装のポイント
A. Firestore セキュリティルール

10段階になるとルールの可読性が重要になるため、関数化して管理します。

JavaScript
function hasAccess(contentData) {
  let user = get(/databases/$(database)/documents/users/$(request.auth.uid)).data;
  return request.auth != null && (
    contentData.visibility == "global" ||
    user.level >= contentData.requiredLevel ||
    request.auth.uid in contentData.permittedUsers ||
    contentData.askerUid == request.auth.uid
  );
}

ひとつ、設計上の「遊び心（Wildcard）」として、「信頼のダウングレード」機能も面白いかもしれません。一度与えた権限を、ログを確認して「不審な動きがあったからL5からL1に落とす」といった、生き物のような信頼関係の管理ですね。

いわゆるオンライン名刺機能のようなものにします。
ですので、アプリケーション側で施せる機能的に機密で管理が必要な部分は、必ずしもWebサイトである必要はありません。
「オンライン名刺」というユースケース、そして「機密性の高い部分は必ずしもWebである必要はない」という方向転換は、設計の現実解として非常に強力です。

Webブラウザには「利便性と拡散性」というメリットがありますが、OSレベルの制御（スクリーンショットの物理的禁止など）には限界があります。一方で、ネイティブアプリ（iOS/Android）を活用することで、ブラウザでは不可能だった「本物の機密管理」が可能になります。

1. ハイブリッド・アーキテクチャ設計
「入り口は広く、奥は深く」を体現するため、Webとアプリで役割を明確に分離します。

レイヤー	実行環境	セキュリティレベル	主な機能

Vault (金庫)	ネイティブアプリ	High (L3-L9)	スクリーンショット完全禁止、GPS/カメラ強制、1回限り表示、詳細Q&A。
2. アプリ側での「究極の機密保護」実装

A. システムレベルのスクリーンショット防止

Android: FLAG_SECURE を設定。OSがスクリーンショット試行を検知し、保存される画像やタスク切り替え画面を自動的に真っ黒（ブラックアウト）にします。

iOS: isSecureTextEntry や専用の UIView オーバーレイを応用し、画面収録やスクリーンショット時に内容を隠蔽します。

B. バイオメトリクス連携

機密情報（Level 7以上など）を開く直前に、FaceID / TouchID を要求。ログイン状態だけでなく、「今まさに本人が見ているか」を再確認します。

C. 強固な監査ログと環境検知

Root/Jailbreak検知: 改造された端末でのアクセスを物理的に遮断。

位置情報: バックグラウンドと連動し、より正確な座標を監査ログに記録。

Antigravity Command Center (ACC) システム構成
管理システムは、「情報の製造」「権限の配分」「状況の監視」の3つのセクションで構成します。

1. Vault Studio (コンテンツ・リンク管理)

ここでは「何を」「誰に」「どう見せるか」を編集します。

ハイブリッド・エディタ:

MarkdownとHTMLのリアルタイムプレビュー。

ABC Shield 設定: コンテンツごとに「コピー禁止」「ブラックアウト（Video変換）」「1回限定」のスイッチを切り替え。

Dynamic Link Generator:

アクセスリンク（Slug）ごとのプロファイル作成。

リンク専用のウェルカムメッセージや、初期解放レベル（L0〜L9）の設定。

有効期限やアクセス上限（n回まで）の管理。

2. User & Trust Controller (ユーザー・権限管理)

登録された全ユーザーの「信頼」をコントロールします。

機能	内容
ユーザーディレクトリ	全ユーザーのリスト。最終アクセス、位置情報、保有デバイスを一望。
レベル・マニュアル操作	特定のユーザーのレベルを 0→9 の間でスライダー操作。
個別指名 (Whitelist)	特定のページやQ&Aだけを「例外的に」許可する個別ID紐付け。
招待状発行	メールアドレスを入力し、特定のアクセスリンクを紐付けた招待メールを一括送信。
3. Forensic & Monitor (監視・監査)

システム内で起きているすべての「動き」を可視化します。

リアルタイム・アクティビティ:

「〇〇さんがリンクAからアクセス」「△△さんがL7閲覧のためカメラ許可を承認」などのログをストリーム表示。

インシデント・アラート:

スクリーンショット試行の検知、位置情報の急激な変化、複数デバイスでの同時ログインを赤字で警告。

ジオ・マップ:

現在アクティブなユーザーが世界のどこにいるかをマップ上にピン留め。

証跡アーカイブ:

閲覧時に強制撮影された「顔写真」と「GPSデータ」を、ユーザーごとに時系列で保存。

技術スタックとセキュリティ
Adminシステム自体が最大の攻撃対象となるため、防御を最優先します。

認証: Firebase Auth ＋ Custom Claims (isAdmin: true)。

4. セキュリティ・ロジック：Level-based Scoping
「Rails Way」に基づき、Pundit や CanCanCan を使わずとも、モデルのスコープでクリーンに権限を制御します。

Ruby
# app/models/content.rb
class Content < ApplicationRecord
  # 10段階レベルの定義
  enum required_level: { level_0: 0, level_1: 1, ..., level_9: 9 }

  # アクセス可能なコンテンツを絞り込むスコープ
  scope :accessible_for, ->(viewer, owner_vault, platform) {
    max_level = (platform == 'web') ? 4 : 9
    user_level = viewer.trust_level_for(owner_vault)
    
    where("required_level <= ?", [user_level, max_level].min)
    .or(where("? = ANY(permitted_user_ids)", viewer.uid))
  }
end

モードの切り替えロジック

Admin モード: 自分の「Vault」の編集、BKC（Rails）との連携、QRコードの提示、監査ログの確認。

Viewer モード: 接続済みユーザーのリスト、相手のレベルに応じたコンテンツ閲覧、カメラ・GPS・イヤホン制約の発動。

Dart
enum BKMode { admin, viewer }

class AppState extends ChangeNotifier {
  BKMode _mode = BKMode.viewer; // デフォルトはViewer
  BKMode get mode => _mode;

  void toggleMode() {
    _mode = (_mode == BKMode.viewer) ? BKMode.admin : BKMode.viewer;
    notifyListeners();

2. セキュアな情報の保管機能 (The Vault Storage)

A. データベース・レベルの暗号化 (Active Record Encryption)

Rails 7以降の標準機能を用い、データベースが盗難に遭っても中身が読めない状態にします。

Ruby
# app/models/content.rb
class Content < ApplicationRecord
  # 秘密鍵を用いた決定論的/非決定論的な暗号化
  encrypts :body, :medical_record, :lgbtq_note
  
  # 検索が必要な項目（例：タイトル）は決定論的暗号化を行う
  encrypts :title, deterministic: true
end
B. 物理的な隔離とゼロ知識への挑戦

Active Storage + S3 SSE: 閲覧時の「顔写真」などは、Amazon S3のサーバー側暗号化（SSE-KMS）を用いて保存。

秘密情報のライフサイクル: 1回限り表示（Burn-after-reading）の設定があるデータは、閲覧完了後のBackground Job（Sidekiq）で物理削除を強制。

C. クライアント側（Flutter）での保管

Secure Storage: APIから取得した一時的なトークンや鍵は、Flutterの flutter_secure_storage（iOS: Keychain, Android: KeyStore）に保存し、メモリ上以外で平文で保持しません。

3. 分析とセキュリティを両立する「監査ログ」
分析用ログとは別に、法的・証拠的な価値を持つ「改ざん不能な監査ログ」を初期から実装します。

監査ログの三要素

Identity: 誰が（Firebase UID ＋ 閲覧時の顔写真スナップショット）

Context: どこで・いつ（GPS座標 ＋ NTP同期された絶対時刻）

Action: 何を（どのレベルの、どのシンボルが付いた情報を見たか）

[重要] ログの不変性:
Railsの before_destroy や before_update コールバックを使い、一度書き込まれた監査ログレコードの変更・削除をアプリケーションレベルで禁止します。

1. モノリス・レンタル（SaaS）構成
1つのRailsアプリケーションで複数の「開示者」を収容するマルチテナント方式を採用します。

テナント分離: 全てのデータは Vault（金庫）モデルに紐付きます。

認証: Firebase Authを使用しつつ、Railsの current_user が「自分のVaultの管理者（Admin）」か「他人のVaultの閲覧者（Viewer）」かを判定します。

2. 権限管理：OTP/URL漏洩の防止（Authorized Access）
「URLを知っていれば誰でも見られる」という状態（いわゆる公開URL）を避け、「認証された特定のユーザーにのみ、特定のリンクを有効化する」仕組みを導入します。

アクセス制御の仕組み

AccessLink (Slug): 開示者が作成するURLは、単なる公開ページではなく「招待券」として機能させます。

紐付け（Binding）: リンクにアクセスした際、システムは「現在のログインユーザー」をチェックします。

認可 (Authorization):

リンクが「特定個人（Email等）」宛てなら、ログインユーザーと一致するか検証。

リンクが「不特定多数（L2レベル等）」宛てでも、「ログイン済みであること」を必須とし、誰がアクセスしたかをその瞬間に AuditLog に記録します。

OTPの使い捨て: 認証が一度完了したリンクは、そのユーザーのセッションに紐付けられ、URL自体を他人にコピーしても他人は閲覧できないようにします。

3. データベース設計（マルチテナント ＆ セキュア保管）
RailsのActive Recordを活用し、初期からログ分析と暗号化を組み込みます。

主要モデル

Account / User: ログインユーザー。

Vault: 各ユーザーの「僕のこと」のルート。

Disclosures: 10段階レベルのコンテンツ。encrypts :body でDB暗号化。

Permissions: vault_id と viewer_id の交差テーブル。

AccessLinks: slug, target_level, max_uses, expires_at。

AuditLogs: viewer_id, content_id, ip, gps, face_snapshot_url, utc_timestamp。

「僕のこと（BK）」における10段階のセキュリティレベル（信頼レベル）を定義します。

このシステムでは、単なる情報の羅列ではなく、「相手との距離感」と「情報の繊細さ」を同期させることで、開示者が安心して自己表現できるグラデーションを作成します。

1. Surface Layer（公開・接点：L0 〜 L2）
誰でも、あるいは緩い繋がりの中でアクセスできる情報です。

Level 0：一般公開 (Public)

対象: URLを知っている匿名ユーザー。

内容: 基本的な名前、現在の肩書き、SNSリンク。

目的: 検索やリンククリックの最初の受け皿。

Level 1：初対面 (Contact)

対象: Web名刺を提示した相手、またはリンクからアクセスした人。

内容: 基本的なポートフォリオ、仕事依頼フォーム、公開用のメールアドレス。

目的: オンライン名刺としての標準的な機能。

Level 2：ソーシャル接続 (Social)

対象: SNS等で既に繋がっている人、または相互フォロー済み。

内容: 少し詳しい趣味、現在の学習内容（例：エンジニアとしての研究テーマ）。

マーク: レインボーシンボル（当事者・連帯の表明）の掲示開始。

2. Trust Layer（信頼・ビジネス：L3 〜 L5）
相互の認識があり、具体的なやり取りが発生する相手に向けた情報です。

Level 3：プロフェッショナル (Business)

対象: 案件の相談者、プロジェクトの同僚。

内容: 詳細な職務経歴、スキルスタック、現在進行中のプロジェクト概要。

目的: 実務的な信頼関係の構築。

Level 4：パートナー (Trusted Partner)

対象: 長期的な取引先、共同開発者。

内容: 稼働状況、連絡がつきやすい時間帯、特定の案件に関する補足資料。

制限: Webクライアントで見せられる情報の限界値（これ以上はアプリ推奨）。

Level 5：機密開示・初級 (Confidential I)

対象: 信頼できる知人、特定の配慮をお願いしたい相手。

内容: ヘルプマークの表示、具体的な配慮事項（持病や特性の概要）。

セキュリティ: 【イヤホン着用必須】音声読み上げはこのレベルから制限開始。

3. Vault Layer（聖域・核心：L6 〜 L9）
アプリ版でのみ解放され、厳格なセキュリティ下で扱われる核心的な情報です。

Level 6：人間関係 (Human Relational)

対象: 親しい友人、信頼できるカウンセラーやメンター。

内容: 価値観の詳細、過去の挫折、ライトなグリーフ（喪失）の共有。

セキュリティ: 動的ウォーターマーク表示。

Level 7：深層カミングアウト (Confidential II)

対象: 深い信頼を寄せている相手。

内容: 障がいの詳細、LGBTQ+に関する具体的な歩み、深いグリーフ。

セキュリティ: 【カメラ顔認識 ＋ GPS取得 ＋ 時刻同期】閲覧中の証跡を完全記録。

Level 8：核心 (Core/Inner)

対象: 家族、生涯のパートナー、最側近。

内容: 持病の核心、緊急時の連絡先、人生の重要な決断に関わる秘密。

セキュリティ: 【一回限り表示】設定可能。閲覧後は物理削除。

Level 9：マスター権限 (Master/Admin)

対象: 自分自身（開示者本人）。

内容: BKC（管理画面）への全アクセス。全てのレベルの編集、全ユーザーの監査ログ閲覧。

目的: 自分の情報の完全な統治。

セキュリティ・マトリクス要約
レベル	主なコンテンツ	セキュリティ制約	音声保護
L0-L2	Web名刺・シンボル表明	特になし（Web可）	制限なし
L3-L4	ビジネス・技術実績	ログイン必須	制限なし
L5	障がい・LGBTQの概要	アプリ推奨	イヤホン限定
L6-L8	核心的カミングアウト	カメラ・GPS・時刻同期	イヤホン限定

L5が「境界線」: これより上の情報は、単にURLをクリックするだけでは到達できません。BKCを通じて、あなたが「相手を信頼した」というアクション（レベル昇格）が必要になります。

音声の「囁き」: L5以上の情報は、スクリーンリーダーがスピーカーから音を出すことを許しません。デバイスが耳に当たっているか、イヤホンがある時だけ「僕のこと」を語りかけます。

また、Level 2以上には、詳細な個人情報の入力を求めます。

1. 刷新されたセキュリティレベル（L0 〜 L2）

Ruby
# app/services/face_detector_service.rb
require 'opencv'

class FaceDetectorService
  # 顔認識用の定義ファイル（OpenCV標準配布のxml）
  CASCADE_PATH = Rails.root.join('vendor/assets/opencv/haarcascade_frontalface_default.xml').to_s

  def self.contains_face?(image_path)
    detector = OpenCV::CvHaarClassifierCascade.load(CASCADE_PATH)
    image = OpenCV::IplImage.load(image_path)
    
    # 顔を検出（AIを使わないパターンマッチング）
    faces = detector.detect_objects(image)
    
    # 顔が1つ以上検出されればtrue
    faces.any?
  rescue => e
    Rails.logger.error "Face Detection Error: #{e.message}"
    false
  end
end

6. セキュリティの考え方：OTPURL の運用
レンタルベース（SaaS形式）での稼働において、友人へのURL共有は以下のように制御します。

ワンタイム・アクティベーション: 友人に送ったURLは、その友人がログイン（L1）した瞬間に、その友人のIDにのみ固定（Bind）されます。

拡散防止: 万が一そのURLが第三者に転送されても、Rails側で「このURLは既に別のユーザーに紐付けられています」と弾くことで、身近な人以外への露出を物理的に遮断します。
